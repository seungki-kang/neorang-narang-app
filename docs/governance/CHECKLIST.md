# 너랑나랑 점검표 1.0

검사 결과: PASS / FAIL / NOT_RUN / BLOCKED. 코드 확인과 실행 evidence를 구분한다.
적용 여부는 검사 결과와 별도 항목으로 기록한다. 기존 N/A는 비적용 사유·근거를 보존하고, UNKNOWN은 필요한 정본·환경 부재면 BLOCKED, 준비됐지만 미실행이면 NOT_RUN으로 분류한다. 일괄 자동 치환하지 않는다.
배포 전 상위 위험 FAIL과 핵심 저장 흐름 NOT_RUN은 해소해야 한다.

서버 인증·RLS·CORS·로그인·결제·AI 비용 제한은 현재 N/A이며 도입 시 재점검한다.

위 N/A 문구는 2026-10-09 로컬 기능 범위의 기존 기록으로 보존한다. 현재 코드 전체에 대한 일괄 비적용 판정으로 사용하지 않는다. [PROJECT_CONTEXT의 후속 PoC 절](PROJECT_CONTEXT.md#후속-코드-확인-로그인동기화-poc-2026-11-01)을 근거로 다음을 개별 재검토한다. 아래는 점검 대상이며 적용 확정·검사 PASS 기록이 아니다.

| 기능·계층 | 재검토 범위와 근거 한계 |
|---|---|
| 로그인·서버 인증 | PoC 클라이언트 로그인·토큰·세션 처리와 서버 계약/실행 증거를 분리한다. 코드 존재만으로 운영 인증을 통과 처리하지 않는다. |
| 동의·동기화 | 합성 완료 큐·송신·철회와 기존 개인 기록 저장을 구분한다. 실제 원문 동기화·공유 동의 완료로 확대하지 않는다. |
| RLS | 서버 DB·정책과 사용자 격리 적용 근거를 별도 확인한다. 클라이언트 로그인으로 RLS 적용을 추정하지 않는다. |
| CORS | 브라우저 통신 계층과 서버 origin 정책에 대해 판단한다. IO HttpClient 요청만으로 CORS 적용·통과를 판정하지 않는다. |
| 결제 | 결제 기능·서버 계약·실행 근거를 별도 확인한다. 로그인 PoC를 도입 근거로 삼지 않는다. |
| AI 비용 제한 | AI 호출·비용 통제 계층의 도입 근거를 별도 확인한다. 로그인 PoC를 적용 근거로 삼지 않는다. |

재검토 시 기능·계층, 적용 여부와 이유, 코드/실행 근거, 검사 결과를 각각 기록한다. 필요한 계약·환경이 없으면 BLOCKED, 준비됐지만 미실행이면 NOT_RUN으로 기록하며 기존 N/A 기록과 16개 점검 항목을 일괄 변경하지 않는다.

300줄/50줄은 분리 검토 신호이지 단독 배포 실패 기준이 아니다.
민감한 예외 원문을 로그로 전달하지 않는다. 앱에 넣은 .env는 비밀키 보관 수단이 아니다.
